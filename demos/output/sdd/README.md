Architecture Overview\n\nThe system adopts a modular, multi-agent architecture orchestrated by the CrewAI framework. This design ensures separation of concerns, making components independently testable and maintainable.\n\n### 🧩 Major Components\n1.  **Ingestion Layer (Input Module):** Responsible for consuming raw data (JSON, CSV, etc.) and normalizing it into a standardized internal format defined by **[SPEC-002]**.\n2.  **Orchestration Engine (CrewAI Core):** The central controller that manages the sequential and parallel execution of agents. It enforces the workflow mandated by **[SPEC-003]**.\n3.  **Specialized Agents (The Workers):** Small, dedicated AI entities, each assigned a specific role and expertise (e.g., `Data_Extractor`, `Semantic_Analyzer`, `Report_Generator`).\n    *   *Interaction:* Agents communicate via structured message passing (Memory Module).\n4.  **Memory Module & Knowledge Base:** Acts as the collective consciousness. It stores conversation history, intermediate results, and retrieved context from the Vector Database (Pinecone/ChromaDB).\n    *   *Function:* Ensures agents have access to all prior decisions and outputs, preventing context loss.\n5.  **Output Layer (Persistence Module):** Formats the final, processed data into the desired output format (e.g., Markdown report, database entry, API payload).\n\n### 🔄 Data Flow Diagram\n*(A detailed Mermaid/UML diagram should be embedded here)*\n\n**Flow:** Raw Input $\to$ Ingestion Layer $\to$ Memory $\to$ Orchestration Engine $\to$ [Agent A] $\to$ [Agent B] $\to$ ... $\to$ Output Layer $\to$ Final Output.\n\n---\n\n## 🔗 4. API Reference\n\nThe project exposes a primary API endpoint for external system integration. All API contracts and required payloads must reference **[SPEC-002]**.\n\n### 🚀 `/api/v1/process`\n\nThis endpoint initiates the full processing workflow for a given input payload.\n\n*   **Method:** `POST`\n*   **Description:** Submits raw data for structured analysis and processing.\n*   **Request Body (JSON):**\n    ```json\n    {\n        \"job_id\": \"string\",\n        \"input_data\": \"[Raw data payload matching SPEC-002 input schema]\",\n        \"workflow_directive\": \"string\" \n    }\n    ```\n*   **Parameters:**\n    *   `job_id` (string, required): Unique identifier for tracking the job status.\n    *   `input_data` (JSON object, required): The raw data to be processed.\n    *   `workflow_directive` (string, optional): Specifies a deviation from the default flow (if applicable).\n\n*   **Response (200 OK):**\n    ```json\n    {\n        \"status\": \"Processing initiated\",\n        \"job_id\": \"string\",\n        \"message\": \"The job is queued and processing will begin shortly. Use /status/{job_id} for updates.\"\n    }\n    ```\n\n### 🔍 `/api/v1/status/{job_id}`\n\n*   **Method:** `GET`\n*   **Description:** Checks the current status of a previously submitted job.\n*   **Path Parameters:**\n    *   `job_id` (string, required): The ID of the job to check.\n*   **Expected Responses:**\n    *   **200 OK:** Returns the current status (e.g., `QUEUED`, `IN_PROGRESS`, `COMPLETED`, `FAILED`).\n    *   **404 Not Found:** If the `job_id` does not exist.\n\n---\n\n## 🤝 5.
